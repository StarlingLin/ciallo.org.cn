# Pull Request 规范

本文适用于向 ciallo.org.cn 提交新的静态小游戏或对现有小游戏进行改造。

## 1. 投稿流程

1. 先搜索现有 Issue 和 Pull Request，避免重复投稿。
2. 新游戏或大规模换皮先使用“游戏投稿 / 改造提案”Issue 表单，说明玩法、代码来源和实现计划。
3. Fork 仓库，从最新 `main` 创建分支，例如 `game/my-game`。
4. 将游戏放入独立目录 `games/<game-id>/`；一个 Pull Request 只提交一款游戏。
5. 完成本地检查和桌面端测试；移动端与触屏测试可选。
6. 按 Pull Request 模板提供必要的游戏与素材基本信息。

自动检查通过只代表结构与基础安全规则合格，最终是否收录仍由维护者人工审核。

## 2. 目录与命名

`game-id` 只允许小写英文字母、数字和连字符，且必须以字母或数字开头和结尾，例如：

```text
games/my-game/
├── index.html
├── game.css
├── game.js
├── game.config.js
├── LICENSE                  # 上游或原创许可证需要时提供
├── UPSTREAM_NOTICE.md
├── ASSET_NOTICE.md
├── README_CUSTOMIZE.md
└── assets/
    ├── images/
    └── audio/
```

必须满足：

- 入口文件为 `games/<game-id>/index.html`；
- 资源使用相对路径，游戏可以在该目录下独立运行；
- 文件名使用小写英文、数字、连字符或点号，不使用空格和中文文件名；
- 不把图片、音频以大段 Base64 塞进 HTML、CSS 或 JavaScript；
- 不提交 ZIP、RAR、PSD、工程缓存、系统临时文件或无关源素材。

## 3. 静态运行与网络边界

投稿必须能以普通静态文件运行，不要求 PHP、Node.js 服务、数据库或外部 API。

不允许：

- 外部 CDN、远程脚本、远程字体、远程图片或运行时下载核心资源；
- 广告、统计、Cookie 追踪、指纹识别、Service Worker 持久化或挖矿代码；
- `eval`、`new Function`、不透明混淆、大段压缩后无法审查的脚本；
- 读取父页面、顶层窗口、主站 Cookie 或与游戏无关的本地存储；
- 未经说明的 `fetch`、WebSocket、`XMLHttpRequest` 或跨域请求。

排行榜只能使用本站提供的同源接口，不能自行上传玩家数据。昵称、成绩和输入必须视为不可信数据。

## 4. 图片、动画与字体

优先顺序：

- 有损或带透明静态图优先使用 WebP；照片可使用高压缩 JPEG；
- SVG 仅用于可信、可审查的矢量内容，不得包含脚本或远程引用；
- 动画优先使用动画 WebP；GIF 仅在文件更小且兼容性确有需要时使用；
- PNG 只用于确实需要无损像素或无法以 WebP 达到要求的素材；
- 字体应优先使用系统字体；必须内置时使用 WOFF2 并说明许可。

硬性限制：

- 单张图片不超过 2 MiB；建议控制在 500 KiB 内；
- 单个字体不超过 1 MiB；
- 单边像素尺寸通常不超过 4096；
- 不保留未被游戏引用的原始大图；确需保留时先在 Issue 中说明。

建议用接近实际显示尺寸的分辨率导出，并在肉眼可接受的前提下降低质量。精灵图应裁掉大面积透明空白。

## 5. 音频与视频

- 短音效优先 OGG/Opus 单声道，通常使用 48～96 kbit/s；
- 背景音乐建议 OGG/Opus 64～128 kbit/s，并裁掉无意义的前后静音；
- 单个音频不超过 3 MiB，建议不超过 1 MiB；
- 不提交无损 WAV 作为网页运行资源；
- 默认不接受视频；确有玩法需要时先建立 Issue 讨论。

游戏首次交互前不得强制播放声音；必须提供清晰的静音/音量控制，并遵守浏览器自动播放限制。

## 6. 总体积与性能

- 单款新增游戏全部运行文件不超过 10 MiB；建议控制在 5 MiB 内；
- 任意单个文件不得超过 5 MiB；
- 首屏只加载开始游戏所需资源，非关键素材应延后加载；
- 动画循环使用 `requestAnimationFrame`，离开页面或暂停时避免无意义计算；
- Canvas 应考虑高 DPI 上限和移动设备性能，不应无限提高渲染分辨率。

超出限制必须先在提案 Issue 中说明原因和替代方案，维护者可以拒绝大体积内容。

## 7. 交互、布局与无障碍

- 最好同时考虑键盘和触屏；
- 页面宽度 320px 起应能正常使用，不出现阻挡游戏的固定元素；
- 明确显示操控方式、暂停、重新开始和静音入口；
- 图像按钮提供可读名称，文本和背景保持足够对比度；
- 游戏需在主站带 sandbox 的 iframe 中完整运行，不得尝试跳出 iframe。

## 8. 首页接入

新增游戏时需要按现有结构同步更新：

1. `index.html` 左侧/顶部游戏标签；
2. `index.html` 首页游戏卡片；
3. 卡片数量和游戏标题；
4. iframe 的 `data-game-src`，必须指向 `/games/<game-id>/`。

首页改动应保持现有视觉语言，不引入外部框架。若不确定卡片设计，可以在 Pull Request 中明确请求维护者协助完成首页接入。

## 9. 来源、许可证与隐私

完整遵守 [素材与许可证边界](LEGAL_AND_ASSETS.md)。`ASSET_NOTICE.md` 最好列出文件名、来源/作者、许可或授权说明、你做过的转换；`UPSTREAM_NOTICE.md` 至少列出上游 URL、固定提交和许可证。

不得提交真实玩家数据、排行榜数据库、访问日志、Cookie、邮箱列表、API Token、SSH 密钥或任何个人隐私信息。

## 10. 本地检查

在仓库根目录运行：

```bash
python scripts/check_site.py .
python -m unittest discover -s server/leaderboard -p "test_*.py"
```

并人工完成：

- 桌面浏览器打开独立游戏页；
- 从主站标签进入 iframe 后游玩、暂停、重开、全屏和保存成绩；
- 使用窄屏/手机尺寸测试触摸操作（可选）；
- 打开浏览器控制台和网络面板，确认无报错、404 和意外外部请求；
- 记录新增资源总体积。

## 11. Review 与合并

维护者可能要求压缩素材、调整碰撞箱、拆分 PR、补充来源或删除高风险依赖。请直接在原 PR 分支持续 push，不要为同一投稿重复新建 PR。

PR 合并后，由 `main` 分支部署工作流更新正式站点；贡献者不会接触生产服务器密钥或排行榜数据库。
